# Performance tests

Driver-overhead benchmarks for clickhouse-matlab.

## What's measured

Two perftest classes:

- `TestInsertPerf` — wall-clock of one `Client.insert(table, data)` call
- `TestQueryPerf` — wall-clock of one `Client.query(sql)` call

Both parameterized over batch size (`rows_1k`, `rows_10k`, `rows_100k`). Tables
use `ENGINE = Memory` to isolate the driver path from server-side storage
variance (no disk I/O, no merges, no compression).

Both suites are additionally parameterized over compression method (`none`,
`lz4`, `zstd`) via the `Comp` parameter, so every measurement is repeated for
each method.

**Loopback caveat:** these benchmarks run against `localhost:9000`, where the
network is essentially free. LZ4/ZSTD therefore mostly show their CPU overhead
and can look like a net loss; the real win from compression appears over a
constrained or remote network. Read the compression numbers as "cost on a fast
link," not "benefit on a slow one."

Excluded from the timed region: connection setup, data generation, table
create/`TRUNCATE`, server-side population in the query suite.

## Running

```bash
./test/run_perf.sh                 # default ClickHouse 25.3, 30 samples per measurement
./test/run_perf.sh 25.8            # different ClickHouse version
SAMPLES=50 ./test/run_perf.sh      # more samples (tighter median, longer wall time)
```

End-to-end flow: build MEX → start ClickHouse container → run both perf
suites → write CSV → tear down → render plots.

## Output

One CSV per run at `bench_results/<utc-timestamp>.csv`. One row per
(suite, test, parameter):

| column | meaning |
|---|---|
| `timestamp` | UTC of the run (shared by every row in the file) |
| `suite` | `TestInsertPerf` / `TestQueryPerf` |
| `test_name` | method name (e.g. `insertMixed`) |
| `parameter` | e.g. `NumRows=rows_10k`, `Limit=rows_10k` |
| `sample_size` | samples collected after warmup |
| `mean_sec`, `std_sec`, `min_sec`, `median_sec`, `max_sec` | per-measurement stats |

Plots (regenerated by `test/plot_perf.py` at the end of every run):

- `bench_results/latest.png` — per-suite layout, log Y. Compares batch sizes
  within each suite. Best for spotting a regression in one batch size.
- `bench_results/latest_by_batch.png` — per-batch layout, linear Y. Compares
  insert vs query within each batch size. Best for reading absolute throughput.
- `bench_results/latest_compression.png` — latest run only. One panel per
  (suite, test), X = batch size, Y = throughput, one line per compression
  method. Directly compares none vs lz4 vs zstd at each batch size.

Throughput is derived: `rows / median_sec`. Both plots annotate each data
point with its value (`8.3ms`, `1.7M`, etc.).

## Reading the results

- The line is `median_sec` — robust to a single slow outlier.
- The shaded band is `±std_sec` (latency) or its translation to throughput.
- Log Y on `latest.png` because batch sizes span ~20×. Linear Y on
  `latest_by_batch.png` because each panel is a narrow range.

Run-to-run variance of 5–15% on the same hardware is normal — that's machine
noise (kernel scheduling, pagecache state, neighbor processes), not driver
behavior. A real regression moves outside the band and stays there across
consecutive runs.

## Reducing noise

Ordered by effort vs. payoff on a shared dev machine.

### Cheap wins

1. **Pin docker and MATLAB to dedicated cores.** Largest single knob —
   removes kernel migration jitter and noisy-neighbor interference.
   ```bash
   docker run ... --cpuset-cpus="0,1" ...
   taskset -c 2,3 "$MATLAB" -batch "..."
   ```

2. **Lock the CPU at fixed frequency for the run, restore after.**
   Stops thermal-driven turbo decay during long runs.
   ```bash
   sudo cpupower frequency-set -g performance
   echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo
   ```

3. **Drop docker log driver and set a memory cap.**
   `--log-driver=none --memory=2g` removes log-write jitter and prevents
   the cgroup from swapping under MATLAB allocations.

### Driver-side wins

4. **Cache `DESCRIBE TABLE` in `ClickHouseClient.insert`.** Currently the
   client does a `DESCRIBE` round-trip on every `insert` call
   (`src/ClickHouseClient.m:184`) to detect column hints. For benchmarks
   with constant schema, this is a full round-trip inside the timed region.
   Either cache by table name or add an `options.skipSchemaProbe` flag.
   Particularly impactful on the 1k batch — DESCRIBE is a meaningful
   fraction of total time there.

5. **Trim the first measured sample** in case the framework's warmup
   wasn't enough — cold pagecache and JIT can bias the first call.

6. **One MATLAB process per suite.** Class-to-class state (MEX caches,
   allocator state) leaks; restart between insert and query suites for
   independent measurements.

### Bigger lever

7. **PR-vs-base delta on the same runner.** Stop chasing stable absolutes
   — run the bench against `main`, then against the PR's HEAD in the same
   job, and compare the ratio. Run-to-run noise cancels because both halves
   see the same temperature, neighbors, kernel state. This is the
   dominant idea in the LLVM/CPython benchmark suites.

### Diminishing returns

- More samples (`SAMPLES=100`). Median tightens by ~1/√N, but machine noise
  already dominates sampling noise at N ≥ 30.
- Dedicated bare-metal runner. Best ceiling, biggest cost.
- `chrt -f` (realtime scheduler), `nosmt` (disable SMT), IRQ affinity.
  Micro-optimizations; only worth it for a regression you can't otherwise
  explain.

## Files

| file | purpose |
|---|---|
| `perf/TestInsertPerf.m` | perftest class — `insert` measurements |
| `perf/TestQueryPerf.m` | perftest class — `query` measurements |
| `test/run_perf.m` | runs both classes, writes `<timestamp>.csv` |
| `test/run_perf.sh` | bash driver: build, start CH, run MATLAB, plot, tear down |
| `test/plot_perf.py` | reads `bench_results/*.csv`, writes the two PNGs |
| `bench_results/` | run artifacts (CSVs + PNGs) |
